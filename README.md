# Go Caches

Исследовательский репозиторий для оценки эффективности различных алгоритмов кэширования под высокой нагрузкой в конкурентной среде.

В стандартных задачах обычно хватает простого LRU, но под высокой нагрузкой в некоторых сценариях он быстро теряет эффективность.

Реализован:
* Набор потокобезопасных кэшей на Go с поддержкой дженериков `[K comparable, V any]` с тестами
* Кольцевой и двусвязный список с поддержкой дженериков. Нет аллокаций на `interface{}` как в стандартном `container/list` и `container/ring`
* Встроенные метрики кэша на атомиках. Считает попадания, промахи, вытеснения, обновления и кол-во проходов в поиске жертвы для вытеснения
* После прогрева кэша 0 аллокаций. Вытесненные элементы переиспользуются
* Обертка для шардирования кэша без false-sharing и единый интерфейс
* Стенд для нагрузочного тестирования кэшей с различными сценариями нагрузки

| Алгоритм | Сложность `Get` | Сложность `Put` (вытеснение) | Устройство |
| :--- | :---: | :---: | :--- |
| **LRU** | `O(1)` | `O(1)` | *Least Recently Used* на двусвязном списке |
| **LFU** | `O(1)` | `O(1)` | *Least Frequently Used* с двусвязными списками частот |
| **LRFU** | `O(1) .. O(log N)` | `O(1) .. O(log N)` | Объединяет LRU и LFU через экспоненциальное затухание весов на базе логарифмической min-heap кучи |
| **SIEVE** | `O(1)` | `O(1) .. O(N)` | Один FIFO-список и указатель `hand` вытеснения. При чтении только устанавливается бит посещения |
| **S3-FIFO** | `O(1)` | `O(1) .. O(N)` | Три FIFO-очереди *Small*, *Main*, *Ghost* и 2-битные счётчики частоты посещения |
| **SLRU** | `O(1)` | `O(1)` | *Segmented LRU*. Делит кэш на испытательный (`In`, 20% capacity) и основной (`Main`, 80% capacity) сегменты |
| **W-TinyLFU** | `O(1)` | `O(1)` | Состоит из входного сегмента *Window LRU* (1% capacity), основного *SLRU* (99% capacity) и фильтра частот *Count-Min Sketch* между Window и Main сегментами |
| **ARC** | `O(1)` | `O(1)` | *Adaptive Replacement Cache*. Состоит из 2 LRU списков живых данных (`T1`, `T2`) и 2 LRU списков истории ключей (`B1`, `B2`). Динамически балансирует размер списков между давностью и частотой |
| **Full-2Q** | `O(1)` | `O(1)` | Входная очередь `A1in`, теневая `A1out` и основной LRU-сегмент `Am`. A1in и A1out работают как FIFO, а Am как LRU |
| **LIRS** | `O(1) .. O(N)` | `O(1) .. O(N)` | Оценивает расстояние между двумя последними обращениями к ключу по метрике IRR. В худшем сценарии требует обрезки стека (stack pruning) до `O(N)` |
| **Clock** | `O(1)` | `O(1) .. O(N)` | Кольцевой буфер с битом второго шанса |
| **Clock-PRO** | `O(1)` | `O(1) .. O(N)` | Развитие алгоритма Clock с кольцевым буфером и тремя указателями для разделения на горячие и холодные страницы |


## Примеры использования

### Одиночный кэш

```go
package main

import (
	"fmt"
	"github.com/ValeriyTyutyunnik/go-caches/caches/sieve"
)

func main() {
	// Создаём SIEVE-кэш на 1000 элементов
	cache := sieve.New[string, int](1_000)

	cache.Put("user:42", 100)

	if val, ok := cache.Get("user:42"); ok {
		fmt.Println("Найдено:", val)
	}

	cache.DeleteKey("user:42")
	fmt.Println("Статистика:", cache.GetStatistic())
}
```

### Шардированный кэш для конкурентной нагрузки

```go
package main

import (
	"github.com/ValeriyTyutyunnik/go-caches/sharded"
	"github.com/ValeriyTyutyunnik/go-caches/caches/wtiny_lfu"
)

func main() {
	// Создаём W-TinyLFU на 100 000 элементов, разбитый на 64 шарда
	// количество шардов округляется до степени 2 вверх, но всегда будет ниже capacity
	cache := sharded.NewSharded[string, string](
		100_000,
		64,
		func(shardCap int) sharded.Cache[string, string] { // конструктор кэша сделан через фабрику, чтобы получить разные реализации кэша
			return wtiny_lfu.New[string,string](shardCap)
		},
	)

	cache.Put("session:abc","payload")
	if val, ok := cache.Get("session:abc"); ok {
		fmt.Printf("do something with %s...\n", val)
		// ...
	}

}
```


## Результаты бенчмарков


### Сценарии нагрузки


Бенчмарки: `bench/workload_test.go`
Результаты: `bench/results/baseline_bench.txt`
Емкость кэшей 10000 элементов

Все реализации прогонялись на 12 логических ядрах по 7 сценариям нагрузки:

* **Uniform (10/90):** равномерный доступ при нагрузке 10% записи, 90% чтения без популярных ключей
* **Pareto (80/20):** 80% запросов приходится на 20% популярных ключей
* **Zipfian:** распределение Ципфа, близкое к реальному веб-трафику и CDN. Основной поток запросов приходится на горячие ключи
* **One-Hit Wonders:** поток уникальных одноразовых ключей для проверки устойчивости к вымыванию полезных данных
* **Sequential Scan:** имитация фонового бэкапа или полного чтения таблицы поверх горячего кэша
* **Moving Hotspot:** резкая периодическая смена популярных ключей. Проверяет скорость адаптации кэша к новым условиям
* **Thundering Herd:** потоки одновременно читают один и тот же ключ, из-за чего возникает сильная конкуренция за доступ к данным

Выводы:

1. `SIEVE` и `S3-FIFO` - лучшие универсальные решения и максимальный RPS. Оба алгоритма лидируют по скорости и HitRate как в одиночном режиме, так и в шардированном режиме.
Они минимально держат блокировку в операциях чтения, показывая лучшую производительность, а также устойчивы к вымыванию ключей в сценарии Sequential Scan. 

`SIEVE` - простейшая реализация и абсолютное лидерство по совокупности скорости и точности.

Минус: немного уступает алгоритмам с затуханием весов в сценариях с резкой сменой трендов. 

`S3-FIFO`: самый быстрый алгоритм в шардированном режиме благодаря отсутствию перестановок элементов в очередях при чтении.

Минусы: проигрывает в сценарии `Pareto` (72.68%) по сравнению с `SIEVE` (76.22%) и `W-TinyLFU` (76.32%). Требует дополнительную память для хранения ключей призраков.

2. Шардирование критически необходимо для алгоритмов `LIRS` и `Clock-PRO`. На большом кэше тратится много времени на очистку стека или проход по кольцу, шардирование снижает нагрузку на эти операции.

`LIRS` один из лидеров по точности на веб-трафике и распределениях Pareto (`Zipfian` - 95.64%, `Pareto` - 76.51%, `Sequential Scan` - 75.00%).

Минус: сложная структура стека с дорогим вытеснением, требуется шардирование. Требует дополнительную память для хранения ключей призраков.

`Clock-PRO` показывает максимальный Hit Rate на распределении Pareto (~77.2%) и лучшую скорость в `Thundering Herd` (84.37 ns).
Минус: дорогое вытеснение при переполнении, требуется шардирование.

3. На равномерной нагрузке и смене трендов `LRU` и `Clock` показывают хорошие результаты, но при потоке одноразовых ключей Hit Rate падает до ~8-10%, а при Sequential Scan до ~55-57%.
Алгоритмы `SIEVE`, `S3-FIFO`, `ARC`, `W-TinyLFU` сохраняют в этих же условиях ~26-29% и ~75% попаданий соответственно.

`LRU` прост в реализации и быстро подстраивается к новым трендам.

Минусы: нет защиты от вымывания одноразовыми запросами и перестановки элементов при каждой операции чтения.

`CLOCK` показывает высокий RPS и быстро адаптируется к новым трендам.

Минус: нет защиты от вымывания одноразовыми запросами.

4. `LFU` отлично защищает горячие данные при фоновом сканировании ~75% Hit Rate, но полностью проваливается в сценарии смены трендов (Hit Rate 12.17% против 71-74% у конкурентов). Ключи, набравшие высокий счётчик в начале теста, навсегда блокируют вход новым популярным данным.
Эту проблему решают гибридные алгоритмы с затуханием или теневыми очередями `LRFU`, `ARC`, `W-TinyLFU`.

`LFU` надежно защищает горячие данные от вымывания.

Минусы: не адаптивен к смене трендов, делает перестановки элементов при каждой операции чтения.

5. `LRFU` быстрее всех адаптируется к смене трендов. Благодаря плавному экспоненциальному затуханию весов `LRFU` занимает первое место в сценарии смены трендов (~74.1% Hit Rate), но уступает в скорости из-за необходимости перестраивать min-heap кучу.

`LRFU` лучше других алгоритмов адаптируется к смене трендов (~74.1% Hit Rate).

Минусы: дорогая перестройка min-heap кучи.

6. `SLRU` показывает высокую адаптацию к смене трендов (~73.6% Hit Rate) и хорошую защиту от вымывания одноразовыми ключами.

Минус: фиксированное соотношение размеров сегментов может оказаться неоптимальным для нагрузки.

7. `W-TinyLFU` и `ARC` дают максимальную точность на сложном трафике, если необходимо получить максимальный Hit Rate и защитить от вымывания дорогие данные. `ARC` работает быстрее за счёт отсутствия затрат на обновление частотного фильтра при каждом обращении.

`ARC` - динамически меняет пропорции очередей и подстраивается под любую нагрузку. Показывает один из лучших средних показателей Hit Rate по всем сценариям (~68%) при высокой скорости (~28-31 ns).

Минус: требует дополнительную память для хранения ключей призраков.

`W-TinyLFU` лидер по Hit Rate в сценариях с веб-трафиком `Pareto` и `Zipfian`, компактно хранит частоты обращений.

Минус: повышенные накладные расходы на обновление хэшей в матрице при каждой операции. Размер окна и сегментов может оказаться неоптимальным для нагрузки.


8. `Full-2Q` занимает промежуточную позицию между простым `LRU` и `SLRU`/`ARC`, обеспечивает защиту от вымывания ключей, но уступает в среднем Hit Rate из-за жестких размеров входной и теневой очередей.

Минус `Full-2Q`: размер сегментов может оказаться неоптимальным для нагрузки. Требует дополнительную память для хранения ключей призраков.

## Почему в кэшах не используется RWMutex при операциях чтения

Показательный эксперимент: `sync.Mutex` против `sync.RWMutex` на базе алгоритма Clock `caches/clock` vs `caches/clockrw`

Алгоритмы `sieve`, `clock`, `S3-FIFO` во время операций чтения не меняют очередность элементов, а только изменяют один флаг или счетчик.
Изменять флаг можно атомарно. Поэтому ожидается, что использование `RLock()` должно ускорить операции чтения под конкурентной нагрузкой.

Замеры показали обратный результат: под высокой конкуренцией за один бакет `RWMutex` проигрывает в 1.5-1.6 раза.

Причины:

Критическая секция на чтение слишком короткая и накладные расходы мьютекса перекрывают возможный выигрыш. 

Также возникает конкуренция за кэш-линию процессора (Cache-Line Contention), когда читатели инвалидируют кэш-линию друг у друга при атомарном изменении счетчика читателей.
Это особенно заметно в сценариях Zipfian и Thundering Herd на шардированном кэше, когда возникает сильная конкуренция за одни и те же данные

- Емкость кэша 100_000 элементов ключ-значение `uint64` + `uint64`. Это 16 байт полезных данных на запись.

Алгоритмы, использующие призрачные очереди, ожидаемо тратят больше памяти. В `LIRS` может храниться больше истории ключей в стеке, чем вмещает сам кэш.

Count-Min Sketch позволяет алгоритму `W-TinyLFU` экономить около 60 байт на каждой записи по сравнению с `ARC` и `S3-FIFO`, решая схожую задачу про знание ключа и получая сопоставимый или более высокий Hit Rate.

Алгоритмы на базе двусвязного списка с метаданными (`SIEVE`, `SLRU`, `W-TinyLFU`, `Full-2Q`, `S3-FIFO`, `Clock-PRO`) хранят в узле структуру `Node[V]`, где после 8-байтового значения `val` идут 1-2 байта флагов или счётчиков. Из-за выравнивания эти 1-2 байта дополняются паддингом до полных 8 байт, добавляя 6-7 байт оверхэда на элемент.
У `Clock` нет двусвязного списка с указателями, поэтому общий расход на запись оказался самым низким, но выравнивание все равно происходит внутри структуры элемента слайса.

Потенциально можно оптимизировать память в перечисленных кэшах. Особенно в `SIEVE` и `SLRU`, снизив расходы на ~35 байт на запись и сделав их самыми компактными. Но это вне задач текущего проекта и имеет смысл только для огромных кэшей с сильным дефицитом оперативной памяти и/или с высокой нагрузкой GC.
